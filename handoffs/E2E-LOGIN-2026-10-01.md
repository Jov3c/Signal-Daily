## 2. 一条用例守住三类缺陷

三类都落在同一条时间线上，且互为上下游，所以**一条**用例足够
（拆成三条的话，上游一坏就收三条红，而其中两条描述的是同一个原因）：

```text
点「发送验证码」
  └─ A 类：代理不通 → 404 → 永远等不到「验证码」输入框
     └─ 填码、点「登录」
        └─ B 类：封套没解 → session.user undefined → 登录整体炸掉
           └─ C 类：登录了但服务端组件没重渲染 → 页面还挂着「登录后才能使用收藏」
```

`/bookmarks` 是**唯一**依赖 Cookie 的**服务端**前台页面 —— 所以只能用它测 C 类。
（`/settings` 的账户区是客户端组件，读 `useAuth()`，登录后本来就会重渲染，**测不出 C 类**。）

## 3. ⚠ 「不许 reload」做成了**可执行**的守卫，不是一句注释

C 类的断言天然脆弱：将来有人为了让用例稳定，在断言前顺手加一句
`await page.reload()` —— 用例就悄悄变成「在测它自己那一次刷新」，**而且永远是绿的**。

所以登录**之前**往 `window` 放一个哨兵；`router.refresh()` 是软刷新会保留它，
`page.reload()` 会换掉整个 JS 环境、哨兵消失。最后一步读回来比对 ——
**用例自己拒绝 reload**。

## 4. ⚠ 顺手补上一个真缺口：`e2e/` 此前**不参与类型检查**

根 `tsconfig.json` 是一个 solution 文件（`files: []` + `references`），
只指向 `packages/*` 与 `apps/*`。**`e2e/**` 和根目录的 `playwright.config.ts`
不在任何 project 的 include 里** —— `tsc -b` 与 `pnpm -r typecheck` 都不会看它们一眼。

这与 `apps/api/test/tsconfig.json` 记的是同一个坑（那里实测曾藏着 3 个真实类型错误）。

补上 `e2e/tsconfig.json` 后**第一次类型检查就抓到一个真实错误**：

```text
e2e/helpers.ts(245,93): error TS2345: Argument of type 'number' is not assignable to parameter of type 'string'.
```

（ioredis 的 `SCAN` 允许 `COUNT 200` 写成数字，而那份手写的局部类型写成了 `string[]`。）

并把这一步接进根的 `typecheck` 脚本，于是 **CI 门禁自动覆盖它**：

```json
"typecheck": "tsc -b && pnpm --filter @signal/web run typecheck && tsc --noEmit -p e2e/tsconfig.json"
```

## 5. 已知限制（如实列出）

### 5.1 ⚠ E2E **没有**进 CI 门禁

它需要 MySQL + Redis + 两份构建产物（分钟级）。与
[`CI-GATE-AND-LEAK-FIX-2026-10-01.md`](./CI-GATE-AND-LEAK-FIX-2026-10-01.md) §5.1 同理：
**我无法在本地验证 GitHub Actions 的 service container 配置**，
而写一个「没验过、又会拦住部署」的 job，风险方向是错的（假红 = 堵死部署）。
**建议单独做一次，并盯着第一次推送。**

### 5.2 harness **不替你构建**，但会**拒绝**跑旧产物

构建是分钟级、用例是秒级；捆在一起会让每次迭代都付构建代价。
代价是「忘了构建」——所以加了**构建新鲜度硬校验**（按 api / web 目标分别比 mtime，
`packages/` 与 `prisma/` 两边都算），源码更新就拒绝运行并给出确切命令。
逃生舱 `E2E_SKIP_FRESHNESS_CHECK=1`。

⚠ 这条不是洁癖：**它正好是牙齿验证的陷阱** —— 注释掉 `router.refresh()` 却忘了重建，
跑出来是绿的，会得出「用例没牙」的**错误结论**。

### 5.3 会清 Redis 的 `ratelimit:auth:*`，因此有硬护栏

`NODE_ENV=production`，或 DB/Redis 的 host 不是 `localhost` / `127.0.0.1` / `::1`
→ **直接拒绝运行**。护栏的**反向测试也做了**（喂 `db.example.com` 与
`NODE_ENV=production`，两次都正确拒绝，exit 1）。

### 5.4 只覆盖登录链路

收藏 / 阅读进度 / 偏好同步的**写路径**没覆盖。将来加用例要注意
`workers:1`（只有一套服务 + 一个 Redis），并复用 `helpers.ts` 而不是复制字面量。

### 5.5 会往库里写数据

每次运行建一个 `e2e+…@signal.local` 用户（登录会 `findOrCreateByEmail`）。
长期跑会积累，按前缀删即可。这是**刻意**换来的：不依赖限流清理是否成功。

### 5.6 端口写死 3000/3001

`next.config.mjs` 的 rewrite 目标在 `next build` 时求值一次并写进
`routes-manifest.json`（实测已是 `http://127.0.0.1:3001/api`）。
端口可配会产生「页面正常、只有 `/api/*` 静默失败」的**迷惑性故障**，所以刻意锁死。

### 5.7 ⚠ 一个副作用需要知情：`pnpm-lock.yaml` 的改动会重新链接 `next`

`next` 把 `@playwright/test` 声明为 **optional peer**，而仓库 `.npmrc` 里有
`auto-install-peers=true`，于是装 `@playwright/test` 会让 lockfile 里
`next@15.5.25` 的解析带上 `(@playwright/test@1.63.0)` 后缀，
**`apps/web/node_modules/next` 会被重新链接**（过程中一度断链，`next build` 报
MODULE_NOT_FOUND，跑一次 `pnpm install` 后恢复）。

已实测 `pnpm install --frozen-lockfile` **exit 0 / Already up to date** ——
CI 不会因此挂。但下次有人装/卸依赖时，如果 `next` 忽然找不到，回来读这一条。
