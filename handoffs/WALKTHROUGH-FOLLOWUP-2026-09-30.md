## 1. 三个 bug 的**根因不同**，所以要三层不同的守卫

这是本轮最重要的结论。把「跑一次浏览器走查」当成一件事来做是错的 ——
`ed0b1a1` 那三个缺陷各自的根因、以及唯一能守住它们的地方，都不一样：

| bug（`ed0b1a1` 修复）                    | 根因                                                 | 唯一能守住的层            | 本轮 |
| ---------------------------------------- | ---------------------------------------------------- | ------------------------- | ---- |
| 本地开发 `/api/*` 全 404（交互静默失效） | dev 形态没有 nginx，浏览器侧走相对路径打不到 api     | 真 HTTP（起 Next 打一次） | 未做 |
| 登录后**整页崩**（`.data` 漏读）         | 「解封套」的责任交给了调用方，**调用方可以忘**       | **单元层**                | ✅   |
| 登录成功但页面不重渲染                   | 服务端组件带着**当时的 Cookie** 渲染，客户端改了状态 | **只有真浏览器**          | 未做 |

## 2. 本轮做了：把「漏读封套」从**会犯的错**变成**写不出来的代码**

### 2.1 解包下沉进 `apiRequest`

```text
改前  apiRequest<{data: T}>(path)  →  调用方自己 .data    ← 可以忘，忘了没人知道
改后  apiRequest<T>(path)          →  拿到的就是载荷      ← 忘不了
```

泛型参数的含义从「封套类型」变成「**载荷**类型」。

### 2.2 类型层再堵一道：`PayloadOnly<T>`

```ts
type PayloadOnly<T> = 'data' extends keyof T ? never : T;
```

`apiRequest` 的返回类型改成 `Promise<PayloadOnly<T>>`。
于是「旧写法」`apiRequest<{ data: X }>(...)` 的返回类型是 **`never`** ——
再读 `.data` 就是**编译错误**。

**为什么需要这一道**（不是重复劳动）：泛型参数是**调用方自己填**的，
TypeScript 只会老实相信它。调用方填 `{data: X}` 而运行时给的是 `X`，
类型检查**不会**发现 —— 这正是那个登录 bug 的形状，只是方向相反。

### 2.3 ⚠ 这道类型守卫**当场就抓到了两处**，值得如实记下

改完 §2.1、加 §2.2 之前，代码里有两处按旧约定写的调用点。
**它们在改动前是正确的**（那时 `apiRequest` 确实返回封套）——
是**我的重构会让它们变成错的**：

| 文件                      | 症状（若不修）                       |
| ------------------------- | ------------------------------------ |
| `admin-daily-actions.tsx` | 日报**发布成功会显示成「操作失败」** |
| `article-client.tsx`      | 「来源与证据」列表**永远打不开**     |

**类型检查在没有 `PayloadOnly` 的情况下抓不到它们** —— 因为调用方填的泛型
自洽地撒了谎。`PayloadOnly` 一加上，`tsc` 立刻报：

```text
admin-daily-actions.tsx(84,27): error TS2339: Property 'data' does not exist on type 'never'.
article-client.tsx(180,21):     error TS2339: Property 'data' does not exist on type 'never'.
```

**这就是「让它写不出来」强于「加测试提醒大家别忘」的实证**：
测试只能覆盖我想到要测的地方，而这两处我一开始没想到。

## 3. 新增 `apps/web/test/client-api.spec.ts`（18 项）

守两件事：

1. **`apiRequest` 是封套解包的唯一发生地** —— 含 204 空响应、载荷本身是 `null`、
   缺少封套时**抛错而不是静默 undefined**、非 2xx 带业务码。
2. **每个导出的请求函数都返回载荷本身** —— 8 个函数一条用例，
   外加一条「导出面守卫」：**新增导出函数却不在表里 → 直接失败**，
   防止将来有人加一个函数绕过封套检查。

### 为什么不用真浏览器

这条性质是「函数返回了什么」，不是「DOM 渲染了什么」。
单元层在这里**更强**：它是**全量**的（每个导出函数都被覆盖），
而浏览器测试只覆盖点到的那个。

### ⚠ 一处设计被我改过，如实记录

最初用的是**对象身份**（`expect(result).toBe(载荷)`），**跑不通**：
载荷要经过一次 JSON 往返（服务端 `stringify` → 客户端 `parse`），
回来的必然是**新对象**，身份相等在此场景恒假。

改成两条互补断言：

```ts
expect(result).toStrictEqual(载荷); // 结构完全相等，封套会多一层
expect(result).not.toHaveProperty('data'); // 直接针对 bug 的形状
```

### 守卫**有牙齿**（已实测）

把 `apiRequest` 改回「不解封套」再跑 → **9 项红**。恢复后 18 项全绿。
（不做这一步的守卫，与一条恒真的断言没有区别。）

## 5. 待裁决（**我没有动**）

### 5.1 ⚠ 本轮之外最重要的发现：**CI 里没有任何测试门禁**

`.github/workflows/deploy.yml` 是**唯一**的工作流，它：

```text
push to main → 构建镜像 → 迁移 → compose up → 探测健康 → 切流量
```

**从头到尾没有一步跑 lint / typecheck / test。** 而仓库里有 1950 个测试。

这意味着：**一个会让登录链断掉的提交，可以直接部署到生产。**
这不是假设 —— `ed0b1a1` 修掉的那个登录 bug 在修复前**一直存在**，
而它所在的提交（Agent 13 的 `7f9921c` / `bcc585c`）是推到了 main 的。

（是否真的部署成功取决于 secrets 有没有配；但**门禁不存在**这件事是确定的。）

### 5.2 Playwright（真浏览器层）—— 这是一个**新增决策**，不是补做既定要求

我核对了全部官方文档，结论是：

- **`docs/17-testing-acceptance.md` 的「必测」25 条里，没有一条要求浏览器测试。**
  其中涉及前端的 4 条（19/20/21/22）都是**静态断言**（token 取值、有无 transform、
  有无某个 UI 元素），并且**已经被 Agent 13 的 34 项视觉守卫覆盖**。
- **`playwright` 这个词在 `01-development-docs/` 与执行规则里一次都没出现过。**
  它只在 `handoffs/` 里以「已知没做」的形式出现。
- `pnpm-lock.yaml` 里出现的 `@playwright/test` 是 **Next.js 的可选
  peerDependency 声明**（`optional: true`），**并没有装进依赖树**。
- 文档没有「新增依赖要走什么流程」的条款；但 `apps/*/package.json` 在
  Agent 00 的允许修改清单里。

所以：**加 Playwright 不会违反任何既定要求，但也没有任何既定要求支持它。**
它唯一能守的是上面表格里的第三行（登录后不重渲染）——
那一行**目前没有任何守卫**，而它已经真实发生过一次。

**代价**：新增 devDependency、一份 `playwright.config.ts`、一套「起真栈」的
装卸（真 MySQL + 真 Redis + api + web），以及验证码的获取方式 ——
验证码是**哈希存储**的（`email_otp_codes.code_hash`），读不了库，
只能从 API stderr 的 `[signal dev-mail] … code=…` 里解析
（`ConsoleMailSender` 在 `NODE_ENV !== 'production'` 且未配 SMTP 时启用）。
本机已有 `chromium-1243` 浏览器二进制，不需要重新下载。

- **C 类（浏览器）**：见 §5.2。
